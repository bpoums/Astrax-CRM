# Architecture

This document describes the system as it currently runs in production. It is
derived from the live Supabase project (`ozbpmrmndkemvvnlnudb`), the deployed
edge functions, and the code in this repository — not from intent or from the
checked-in migrations, which are behind the live schema (see
[database.md](database.md)).

## Stack

- **Frontend**: TanStack Start (file-based routing via `@tanstack/react-router`,
  SSR shell) + React 19 + Tailwind v4 + shadcn/ui (Radix primitives).
- **Backend**: Supabase — Postgres, Row-Level Security, `SECURITY DEFINER` SQL
  functions as the write API, three Edge Functions, `pg_cron` for scheduled
  jobs, `pg_net` for outbound HTTP from triggers.
- **Deployment**: built with Vite, deployed as a Cloudflare Worker via
  Wrangler. Not deployed to Vercel or Netlify despite the project's Lovable
  origins.
- **State/data fetching**: TanStack Query (`@tanstack/react-query`) everywhere;
  no separate global client-state store. Supabase Realtime (`postgres_changes`
  channels) invalidates queries on `submissions` changes rather than the app
  polling.
- **File parsing/export**: `papaparse` and `xlsx` (SheetJS), both used
  client-side only — for reading uploaded spreadsheets and for the Exports
  tab's CSV/Excel downloads.
- **Origin**: the project was scaffolded on [Lovable](https://lovable.dev) (see
  `AGENTS.md`, `.lovable/`, and `src/lib/lovable-error-reporting.ts`, which
  reports uncaught render errors from `src/routes/__root.tsx`'s error boundary
  back to the Lovable platform). Development has since moved to this
  repository directly; `README.md` is stale Lovable boilerplate from an
  earlier, unrelated project name ("Workflow Explorer") and should not be
  treated as current documentation.

## Request flow

```
Browser (React) ──reads──> Supabase Postgres, scoped by RLS
Browser (React) ──writes─> Supabase RPC (SECURITY DEFINER function) ──> Postgres
Browser (React) ──invokes─> Supabase Edge Function (invite-user) ──> auth.admin API
Spreadsheet lead ──> ingest-sheet-lead Edge Function ──> ingest_sheet_lead() RPC ──> Postgres
Postgres trigger (INSERT/UPDATE on submissions) ──net.http_post──> sheet-sync URL ──> Google Sheets (Apps Script)
pg_cron (every minute / daily) ──> expire_stale_reviews() / purge_payment_data() / purge_old_reporting_leads()
```

There is **no application server** in the traditional sense — the Cloudflare
Worker serves the built SPA/SSR shell; all business logic that matters for
correctness or security lives in Postgres (RLS policies and `SECURITY DEFINER`
functions), not in the Worker or in React.

## Security model (see [authentication.md](authentication.md) for detail)

The database is the enforcement boundary, not the client:

- Every read goes through Row-Level Security, scoped by `my_role()` (a
  `SECURITY DEFINER` SQL function reading `profiles.role` for the current
  `auth.uid()`, and returning nothing if the profile is `active = false`).
- Every write goes through a `SECURITY DEFINER` RPC that re-checks the role
  itself (`if my_role() not in (...) then raise exception 'not authorized'`).
  As of this audit, only **one** table has a client-reachable direct RLS write
  path: `profiles`, and only for an admin (`admin manages profiles`, `FOR ALL`).
  Every other table — including `submissions` — has **no** RLS write policy at
  all; every mutation on it is a named RPC. (`CLAUDE.md`'s older note that "a
  manager or admin may update `submissions.payload` directly" is stale — that
  path has been replaced by the `update_payload_field` RPC. See
  [decisions/0002-payload-writes-via-rpc.md](decisions/0002-payload-writes-via-rpc.md).)
- `src/lib/auth.tsx`'s `requireRole()` route guard is cosmetic: it keeps a role
  off a screen that would show it nothing, but grants no access by itself.

## Directory map

| Path | What lives there |
|---|---|
| `src/routes/` | File-based routes. `_authenticated/` is the auth-gated tree; `_authenticated/cx/` is a nested layout route for the four CX-pipeline tabs. |
| `src/components/` | All screens and their pieces — one file per screen/feature, no further nesting. |
| `src/lib/` | Non-visual logic: `auth.tsx` (session/role context + route guard), `carriers.ts`, `centers.ts`, `cx-status.ts`, `lead-search.ts` (server-side search clause builders), `format-date.ts`, `payment-summary.ts`, `duplicate-ssn.ts`, `field-mask.ts`, `form-fields.ts`, `form-warnings.ts`, `canonical-fields.ts`, `parse-file.ts`, `function-error.ts`, and `normalize/` (the deterministic import-normalization engine — see [features/spreadsheet-import.md](features/spreadsheet-import.md)). |
| `src/integrations/supabase/` | `client.ts` (Supabase client) and `types.ts` (generated by `npm run types` — never hand-edited). |
| `supabase/migrations/` | **Not the source of truth.** Only two migration files exist locally; the live schema has diverged substantially (dozens of tables/functions/views exist live that are absent from these files). Treat the live project as authoritative — see [database.md](database.md). |
| `supabase/config.toml` | Declares `project_id = "pqvnfqwtojdaxwewbaal"` — this does **not** match the actual live project ref (`ozbpmrmndkemvvnlnudb`, used everywhere else: `npm run types`, the deploy docs, `CLAUDE.md`). This file appears stale/disconnected and should not be trusted to identify the live project. |
| Root `*.md` files | `CLAUDE.md` (engineering rules, kept current by this audit), `PRODUCT.md` (business/product framing), `WHERE-TO-CHANGE.md` (a task-oriented "where do I edit X" index), `AGENTS.md` (Lovable git-history notice), `README.md` (stale, ignore). |

## Roles

Nine `app_role` enum values exist in the live database:
`admin`, `closer`, `manager`, `validator`, `data_uploader`, `cxm`, `cxa`,
`closing_manager`, `general_manager`. See [authentication.md](authentication.md)
for what each can reach, and [multi-tenancy.md](multi-tenancy.md) for how
`closing_manager` is scoped to one center while `general_manager` is not.

## Known structural gaps (not fixed by this audit — see individual feature docs)

- Three of the four CX-pipeline tabs (Transfer, Chargeback, Analytics) are
  routed and guarded but render a literal "Coming soon" placeholder
  (`CxPlaceholder` in `src/components/cx-shell.tsx`). Only "Customers Pipeline"
  is built. See [features/cx-lifecycle.md](features/cx-lifecycle.md).
- `supabase/config.toml`'s project id mismatch (above) means `supabase` CLI
  commands run against this repo's local config would target the wrong
  project unless the id is corrected or overridden.
